🟢 Continuous Delivery and the DORA Model

#Summary / Introduction

Continuous Delivery (CD) is a discipline in which software is continuously kept in a state suitable for deployment to production, so that releasing a new version becomes a routine, low-risk activity that can be performed on demand. Continuous Delivery is also one of the few approaches for which there is a statistically proven relationship between its adoption and improvements in an organization's business results. This conclusion is based on extensive research conducted over multiple years, described in the book Accelerate (Forsgren, Humble, Kim), and on the subsequent DORA model (DevOps Research and Assessment).

For an architect, this topic is important because the ability to deliver frequently and safely is largely a property of the architecture (the ability to deploy independently, testability, deployment units), not merely a property of CI/CD tools. For testing, this topic is essential because fast and reliable delivery is not possible without an automated testing safety net that provides confidence in every change.

#The Causal Chain of the DORA Model

The DORA model is not just a set of metrics; it defines a clear causal relationship (research-based causal model):

Capabilities (Capabilities) → Software delivery performance (Delivery performance) → Outcomes (Results)

This is read as follows: building specific technical, process, and cultural capabilities improves measurable delivery performance, which is then reflected in both organizational results and people's satisfaction. The arrows represent a proven statistical relationship, not mere correlation.

#1. Software Delivery Performance (4 Key Metrics)

Delivery performance is measured purely through data using four metrics that cover two seemingly opposing axes – Speed / Throughput and Stability / Stability. A fundamental research finding is that top-performing teams do not make a trade-off between speed and stability – they excel at both simultaneously (speed and stability reinforce each other; they are not opposites).

Metric Axis What It Measures
Deployment frequency Speed How often the organization deploys code to production
Change lead time Speed The time from a code commit to its deployment in production
Change fail percentage Stability The proportion of deployments that cause an outage or require a rollback or hotfix
Failed deployment recovery time (MTTR) Stability The time needed to restore the service after a failed deployment

Additional note: More recent editions of the DORA research add reliability (operational reliability / meeting agreed operational objectives) as a fifth dimension. However, the four basic metrics remain the core of the model.

#2. Capabilities (What Needs to Be Improved)

To improve the metrics, teams must build technical, process, and cultural capabilities. The most frequently mentioned accelerators include:

  • Continuous Integration & Trunk-based development (technical capability): Developers integrate code into the main branch (trunk/main) daily and avoid long-lived feature branches. A broken build has the highest priority and is fixed immediately (ideally within minutes). This ensures rapid feedback and small changes that are easy to verify.
  • Loosely coupled architecture & teams (architectural capability): The architecture allows teams to make extensive changes and deploy independently, without lengthy coordination with other teams. This “testability and deployability without dependencies” is the strongest architectural predictor of performance – it minimizes waiting and orchestrated releases.
  • Generative culture according to Westrum (cultural capability): Unlike a pathological (power-oriented) or bureaucratic (rule-oriented) culture, this is a performance-oriented (generative) culture. It is safe to share bad news; failure is not punished but treated as an opportunity to improve the system. Responsibility and risks are shared.

#3. Outcomes (Impact on Both the Company and People)

Properly implemented CD delivers results on two levels:

  • Organizational performance: Commercial and non-commercial success – greater profitability, market share, operational efficiency, and better achievement of corporate and mission objectives.
  • Well-being (people's satisfaction): Productivity and job satisfaction increase, burnout (burnout) decreases significantly, unplanned work and firefighting (rework) are reduced, and fear of deployment (deployment pain) disappears.

#Definitions and Basic Concepts

Concept Definition Significance for Architecture Significance for Testing Typical Misconception
Continuous Delivery A practice in which software is always in a state suitable for deployment. Requires deployable, loosely coupled units. Impossible without an automated testing pyramid. Confused with Continuous Deployment.
Continuous Deployment Automatic deployment of every successful change all the way to production without a manual step. Requires even greater confidence in the pipeline. Full test automation + monitoring are necessary. Considered a synonym for CD.
Continuous Integration (CI) Frequent (daily) merging of changes into a shared branch with an automatic build and tests. Leads to small units that can be integrated. Rapid feedback from automated tests. Reduced to merely “we have a build server.”
Trunk-based development Working on the main branch, with short-lived feature branches or none at all. Reduces integration debt and merge risk. Feature toggles + good tests are necessary. Confused with “no code review.”
DORA metrics 4 delivery performance metrics (frequency, lead time, change fail %, MTTR). Measure the consequences of architectural decisions. Change fail % and MTTR measure test effectiveness. Viewed as a target, not an indicator.
Westrum: generative culture A performance-oriented culture in which it is safe to report errors. Enables shared ownership of the architecture. Encourages open reporting of defects and risks. Confused with “safety without accountability.”
Deployment pipeline The automated path of a change from a commit through tests to production. Reflects the system's deployment and integration boundaries. Orchestrates the individual levels of testing. Understood only as a tool, not as a process.

#Common Mistakes and Anti-patterns

  • Confusing Continuous Delivery and Continuous Deployment.

    • Why it is a problem: It leads to misunderstandings about the degree of automation and risk. CD guarantees readiness for deployment; Continuous Deployment deploys automatically without manual approval.
    • How it manifests: The team claims to be “doing CD,” but in fact deploys manually once a quarter.
    • Prevention: Consistently distinguish the two concepts and explicitly identify where the manual decision gate is.

  • Optimizing only one axis (speed OR stability).

    • Why it is a problem: It contradicts the key DORA finding – these axes are not in opposition. Pressure on deployment frequency alone, without a testing safety net, increases change fail %.
    • How it manifests: A growing number of hotfixes, long MTTR, a “Friday deployment freeze.”
    • Prevention: Track all four metrics together as a balanced system.

  • CD built on a tightly coupled (tightly coupled) architecture.

    • Why it is a problem: Independent deployment is impossible; every release requires orchestration across many teams.
    • How it manifests: A “release train,” long merge phases, coordination meetings before deployment.
    • Prevention: An architecture with clear boundaries and independent deployability/testability of components.

  • Metrics as a target (Goodhart's Law).

    • Why it is a problem: When a metric becomes a target, it ceases to be a good metric – teams start “deploying empty commits.”
    • How it manifests: Metrics increase, but customer value does not.
    • Prevention: Use metrics as an indicator of system health, not as an individual KPI.

  • CD without test automation (a missing safety net).

    • Why it is a problem: Fast deployment without tests only delivers defects to production faster.
    • How it manifests: High change fail %, manual regression testing as an impediment.
    • Prevention: A healthy testing pyramid (more fast unit tests, fewer slow E2E tests) integrated into the pipeline.

  • Focusing on tools instead of culture.

    • Why it is a problem: Buying CI/CD tools will not change a pathological culture in which mistakes are punished.
    • How it manifests: People hide problems, low psychological safety, rework.
    • Prevention: Deliberately build a generative culture (blameless postmortem, shared responsibility).

#Examination Questions

Basic Level

  • What is Continuous Delivery, and how does it differ from Continuous Deployment? → The answer should include the definition of an “always deployable state” and the difference between a manual and an automatic gate to production.
  • Name the four DORA metrics and assign them to the speed/stability axes. → Frequency + lead time = speed; change fail % + MTTR = stability.

Intermediate Level

  • Explain the causal chain Capabilities → Performance → Outcomes. → Emphasize that this is a proven relationship from the Accelerate research, not a correlation.
  • Why are speed and stability not mutually exclusive? → Small changes, rapid feedback, and automation improve both at once.

Advanced Level

  • How does architecture affect the ability to practice CD? → Loosely coupled / independent deployability and testability are the strongest predictor; mention deployment boundaries.
  • What is the role of Westrum's culture model in CD? → A generative culture enables blameless handling of errors, which improves the system through feedback.

Questions about Practical Experience

  • How did you measure or improve one of the DORA metrics in your project? → Specific measures: trunk-based development, feature toggles, speeding up the pipeline, reducing batch size.

Decision / Trade-off Questions

  • When should full Continuous Deployment not be introduced? → Regulated/safety domains where a manual gate, certification, or an audit is required; CD yes, automatic deployment no.
  • How can delivery speed and the cost of test automation be balanced? → A risk-based approach, a testing pyramid, investment where risk and change fail % are highest.

#Model Examination Answer

“Continuous Delivery is a discipline in which software is continuously kept in a state suitable for deployment to production, so that releasing a new version is a routine, low-risk activity performed on demand. It is important to distinguish it from Continuous Deployment, where every successful change is deployed to production automatically without a manual gate.

The importance of this topic is supported by research – the book Accelerate and the DORA model have demonstrated a statistical relationship between adopting CD and improving organizational results. DORA describes a causal chain: building abilities (capabilities) improves delivery performance (performance), which is reflected in company results and people's satisfaction (outcomes).

Delivery performance is measured using four metrics along two axes: speed (deployment frequency, change lead time) and stability (change fail percentage and recovery time MTTR). The key finding is that top-performing teams do not make a trade-off between speed and stability – they achieve both simultaneously because small, frequently integrated changes are easier to test and fix.

From an architectural perspective, the most important capability is a loosely coupled architecture that allows teams to deploy independently. Without it, every release requires orchestration and speed decreases. From a testing perspective, CD is impossible without an automated testing safety net – a healthy testing pyramid – because that is precisely what provides confidence in every change; change fail % and MTTR directly reflect the quality of this safety net. Culture also plays a role: according to Westrum, a generative culture is needed, in which it is safe to report errors.

A practical example is the introduction of trunk-based development with feature toggles and a faster pipeline: smaller batches of changes reduced change fail % and shortened lead time at the same time. However, trade-offs must be considered – in regulated or safety domains, we typically retain a manual approval gate, so we practice Continuous Delivery, but not fully automatic deployment; and we manage investment in test automation according to risk.

In summary: Continuous Delivery is a demonstrably effective approach to improving organizational results; it is based on a loosely coupled architecture, strong test automation, and a generative culture, and is measured using four balanced DORA metrics.”

#Short Version for Quick Review

5 Main Points

  1. CD = software is always in a state suitable for deployment; ≠ Continuous Deployment (automatic deployment).
  2. DORA chain: Capabilities → Performance → Outcomes (a proven relationship, not correlation).
  3. 4 metrics = 2 axes: speed (frequency, lead time) + stability (change fail %, MTTR).
  4. Speed and stability are not mutually exclusive – top-performing teams have both.
  5. Key accelerators: trunk-based/CI, loosely coupled architecture, generative culture.

5 Key Concepts Continuous Delivery · DORA metrics · Trunk-based development · Loosely coupled architecture · Westrum generative culture.

#Learning Outcome

After mastering the topic, the student is able to: define Continuous Delivery and distinguish it from Continuous Deployment and Continuous Integration; explain the causal chain of the DORA model and interpret the four key metrics along two axes; justify why speed and stability are not in opposition; describe the architectural prerequisites for CD (a loosely coupled, independently deployable and testable architecture) and the role of test automation as a safety net; and discuss the trade-offs of introducing CD in both ordinary and regulated (safety) environments.

#Practical Example: Continuous Delivery in Embedded Development

Presentation: In an embedded project, we attempted to come as close as possible to the principles of Continuous Delivery, but encountered physical limitations arising from our dependence on the target hardware. The following analysis shows which capabilities according to the DORA model we managed to achieve and where the limitations remain.

Our setup (deployment pipeline). We apply strong automation already at the feature branch level (unit tests and virtual functional tests). Merging (merge) into the integration branch through a Pull Request is conditional on a nightly run on a Hardware-in-the-Loop (HIL) test rig. A release to the main branch (main) runs on demand – it automatically generates tags, packages artifacts, compiles documentation, and runs static analysis with coverage reports.

Applying the theory – comparison with the DORA model:

  • Continuous Integration & deployment automation (achieved): We fulfill this capability well. The release pipeline generates a complete package without manual intervention, and failing tests at a lower level immediately block the merge – the principle that “a broken build has the highest priority” therefore works.

  • Change lead time (bottleneck): We encounter the physical limits of the hardware. Rapid feedback (fast feedback loop) is delayed because a full HIL test runs only at night due to capacity constraints – waiting for the morning result conflicts with the ideal of CI, where feedback and correction are measured in minutes. Lead time is further extended dramatically by a subsequent external system test, which prevents a straightforward deployment directly to production.

  • Change fail percentage (strength): Thanks to a strict Quality Gate (a merge is not accepted until it passes the HIL test), we maintain very high stability and minimize the proportion of defective releases.

Conclusion: In embedded development, we have built the maximum achievable level of Continuous Integration. Two systemic limitations hold us back from moving to pure Continuous Delivery (measured according to the DORA metrics): the physical latency of testing on real hardware and the dependency on a manual/external system test before production. This is a clear illustration that key metrics (particularly lead time) in the embedded domain are constrained more by the architecture of the testing environment than by the maturity of CI/CD tools.
