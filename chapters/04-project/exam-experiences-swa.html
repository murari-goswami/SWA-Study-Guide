SWA Certification — Exam Experiences & Model Answers

Compiled from exam experiences of Armen, Patrick, Enrico, and Navneet. All answers use the Siemens SWA learning content.

Exam Experience by Armen

Assessors from SHS Format: Present yourself, 15 min project presentation, 10 questions from 5 topics (2 min theory + 4 min practice each, ~60 min total), 20 min wait, 15 min result

#1. Systematic SW Architecture Design

Q: Tell me the theory? How do you do it in your project?

The primary method is the L-Model, which defines a systematic workflow from assignment to implementation:

  • Vertical Phase (Analysis): Requirements elicitation, domain model creation, modeling scenario dynamics, determining scope & boundaries
  • Horizontal Phase (Design): First conceptual draft, baseline architecture structuring, deployment views, defining principles & guidelines, planning/realizing increments

The key discipline is that the entire L-model is traversed in every iteration — phases with nothing to do become a no-op but are never excluded. This distinguishes it from a generic PDCA cycle.

Architecture is driven by the equation: Forces + Creativity + Communication + Decisions, where Forces = Requirements + Constraints. These forces define the solution space, whose size is described by the term "Freedom of Choice".

Additional key concepts:

  • ASR identification using the "5 miles wide, 5 inches deep" method — shallow scan across all requirements, then deep dive only on high-risk candidates
  • Pyramid Model — limiting documentation to 3 levels: System → Subsystem → Component
  • Architecture maturity stages: Initial Draft → Walking Skeleton → MVP → MMP/MLP
  • Conway's Law and the Inverse Conway Maneuver — deliberately designing the architecture to match the desired team/communication structure

In practice: The L-model is applied iteratively. Each increment re-enters the vertical phase; phases with nothing new become a no-op but are never dropped. This keeps boundaries and deployment from silently rotting. Event Storming workshops serve as a practical domain modelling technique — producing domain model, dynamics, and stakeholder alignment in one session.

#2. Architecture Assessment (Review)

Q: What method are you using for architecture assessment?

Three qualitative review methods exist:

Method Interaction Duration Strength Key Restriction
Active Design Review (ADR) Designer + reviewer 2 days/reviewer Focused defect finding via challenges Small scale only
Industry Practice Review Interviews 4 weeks (1-day flash variant) Proposes concrete measures Requires experienced reviewers
ATAM Workshop 2 weeks Deep trade-off analysis of quality scenarios Proposes no measures

ATAM in detail: Scenario-driven method that produces:

  • Sensitivity Points — architectural decisions that affect a single quality attribute
  • Tradeoff Points — decisions that affect multiple quality attributes
  • Risks — potentially problematic architectural decisions
  • Non-Risks — good decisions confirmed by analysis
  • Risk Themes — systemic patterns across individual risks

These feed into the ATAM Matrix linking scenarios, architectural decisions, sensitivity points, and tradeoffs.

Key insight: ATAM and Industry Practice are complementary — ATAM tells you what the problem is, Industry Practice tells you what to do about it.

What triggers a review (situations/events):

  • Project phase transitions — inception needs scenario-based reviews (ATAM), construction needs repeated ADRs, transition needs experience-based reviews
  • Architecture drift or erosion detected — code diverges from the planned design (conformance check fails)
  • Architecture smells identified — cyclic dependencies, overlayered design, paper tiger architecture
  • Quality metric thresholds breached — e.g., Sonar maintainability drops to red
  • Major architectural decisions pending — before committing to an expensive, hard-to-reverse decision
  • Process gates — formal checkpoints that mandate a review before proceeding

Who initiates (roles with authority): Architect (drives within scope), Enterprise Architect (cross-project governance), Process (formal gates), Developer (raises code-architecture divergence), QM (compliance).

In practice (Armen's approach): Using DI MC review tool with other architects — a form of peer review that combines elements of Active Design Review (structured review with domain experts) and the "Everything as Code" philosophy for architecture conformance checking.

Quantitative methods complement qualitative reviews: Code Quality Assessment (ArchUnit for architecture conformance), Simulation, and Prototyping.

#3. Architecture Refactoring vs. Code Refactoring

Q: What is the difference between architecture refactoring and code refactoring?

Both share the same principle: external behavior remains the same.

The critical difference lies in scope and what changes internally:

Aspect Code Refactoring Architecture Refactoring
Scope Class level (local) Component / Subsystem / System level
What changes Internal code structure (variable names, method extraction, class decomposition) Internal module structure — layering, component boundaries, dependencies, service decomposition
What stays the same External behavior and interfaces External behavior and interfaces
Who decides Developer — daily work Team/PO (Backlog item) to CTO (standalone project)
Cost/Risk Cheap, continuous More expensive, requires business case
Impact on artifacts Code only Code + Documentation + Integration Tests

Architecture refactoring reorganizes the logical structure of modules and components — how code is grouped into layers, how dependencies flow between components, which service owns which responsibility. Code refactoring restructures within a single module without changing module boundaries.

Example: Extracting a method is code refactoring. Breaking a cyclic dependency between two services by relocating an entity to a different bounded context is architecture refactoring — the module structure changes, but the external API remains identical.

Levels beyond refactoring:

  • Reengineering: Taking apart the system (reverse engineering) and rebuilding it (forward engineering) — standalone project
  • Rewriting: Throwing away old code entirely — extremely costly and risky, last resort

#4. Architecture Documentation — Views and Purpose

Q: Views in architecture documentation and for which purpose?

Architecture cannot be described with a single diagram. Different stakeholders need different views.

4+1+n Views concept:

View Purpose Target Audience
Use Case View System behavior from the user's perspective End users, business analysts
Logical View Functional structure and decomposition End users, designers
Process View Runtime behavior, concurrency, performance, scalability System integrators, performance engineers
Implementation/Development View Code organization, modules, packages Developers
Physical/Deployment View Topology, hardware, communication, installation Systems engineering, DevOps
Additional views (+n) Context, Data, Variability, Migration Various

C4 Model (Modern alternative):

Level What it shows Target Audience
Context System in its environment, external actors Management, business, non-technical stakeholders
Containers Major building blocks (apps, databases, message queues) Architects, DevOps, developers
Components Internal structure of one container Developers
Code Class-level detail (UML) Developers (use sparingly — becomes outdated quickly)

Templates:

  • arc42 — popular structured template. Advantage: structure. Risk: may be incomplete or overloaded. Rule: never delete any section from a template.
  • Siemens template — organization-specific variant

Rules and best practices:

  • Process documentation with same quality attention as code (versioning, change management, refactoring)
  • Every document must have one definitive owner
  • Documentation overview should not exceed 50 pages
  • Keep documentation current, "but not too current" — review regularly
  • Write from the reader's perspective, avoid repetition and ambiguity

#5. Risk-Based Testing

Q: Do you do risk assessment? Why do you use RBT?

Risk-Based Testing prioritizes testing effort where Risk = Likelihood x Impact is greatest — because exhaustive testing is impossible with limited resources.

Why use RBT:

  • Optimizes limited testing budget by focusing on highest-risk areas first
  • Provides stakeholders with transparent risk-based decisions (test vs. accept)
  • Creates traceability between business risks and test coverage
  • Supports informed exit criteria — "we tested the top 80% of risk exposure"

Two types of risk:

  • Product Risk (Quality Risk): The system may fail to meet requirements — mitigated through testing
  • Project Risk (Planning Risk): Threatens the ability to deliver — managed through contingency, not testing

5-step process:

  1. Risk Identification — expert interviews, defect logs, architectural ambiguities
  2. Risk Analysis — assign Probability and Impact → Risk Exposure
  3. Risk Response — calculate RPN (Probability x Impact x Detectability), assign test techniques
  4. Review & Decision — stakeholder agreement on test vs. accept
  5. Test Planning & Allocation — translate to test levels, assign responsibility

3 Amigos approach for joint risk assessment: PO (knows business impact), Developer (knows code complexity), QA (knows detection difficulty).

Methods: Lightweight (PRAM, PRisMa) for standard projects; Heavyweight (FMEA, FTA) for safety-critical systems.

#6. Design for Testability

Q: Theory and practical application?

DFT rests on two fundamental pillars:

  • Controllability: Ability to supply inputs, induce required states, reset to known state
  • Observability: Ability to monitor outputs, internal states, side effects, error conditions

A third supporting pillar is Isolability — testing a unit in isolation from its dependencies.

Architectural tactics:

  • Dependency Injection / IoC — replace dependencies with test doubles
  • Layered/Hexagonal architecture (Ports & Adapters) — isolate business logic from infrastructure
  • Humble Object pattern — extract testable logic from hard-to-test environments (GUI, HW)
  • Testability interfaces — dedicated diagnostic/control interfaces (protected in production)

Testing methodologies supporting DFT:

  • TDD — Red-Green-Refactor cycle; primarily a design technique
  • BDD — Given-When-Then executable specifications bridging business and technical teams

James Bach's dimensions of testability: Intrinsic, Practical, Epistemic, Project-related, Subjective, Value-related.

Trade-offs: Testability vs. Encapsulation, vs. Performance (abstraction overhead), vs. Security (test interfaces as attack surface).

#7. Non-Functional Requirements

Q: What are the 3 major NFRs in your project and why?

The architect must identify, prioritize, and make NFRs concrete. Common top-3 pattern:

Quality Business Justification
Availability Business-critical — downtime directly impacts revenue and customer trust
Interoperability Not an end-to-end solution — must integrate with the existing system landscape
Security Organization must be a role model — security is a strategic identity

How to obtain NFR information:

  1. Service Description including SLAs — measurable quality targets
  2. Quality Attribute Workshops (QAW) — 8-step SEI methodology for structured elicitation
  3. Utility Tree — classify quality attributes by importance and feasibility risk (H/M/L)
  4. Quality Attribute Scenarios — 6-part template (Source, Stimulus, Artifact, Environment, Response, Measure) turns vague NFRs into testable specifications
  5. 5 Whys and product comparison/customer visits — uncovering actual needs behind vague statements

Conflict resolution is key: extreme security reduces performance, high availability drives up cost. The architect documents trade-offs transparently and negotiates over-aggressive requirements.

#8. Understanding Requirements — Clarification Story

Q: Tell about a time when you didn't understand a requirement and how you clarified it

SWA approach to clarification:

  1. Recognize the gap early — apply the "5 miles wide, 5 inches deep" scan to spot ambiguity before committing to implementation
  2. Communication to source — go back to stakeholders directly, don't guess. Use the 3 C's (Card, Conversation, Confirmation)
  3. Visualization — draw what you mean:
    • State Diagrams — reveal all possible states and transitions, exposing missing edge cases
    • Sequence Diagrams — show component interactions over time, revealing timing dependencies
  4. Apply SOPHIST/MASTeR template — force structure: [Condition] - [Actor] - [Obligation] - [Action] - [Object] - [Qualifier] to eliminate "weasel words"
  5. BDD/Gherkin — write Given-When-Then acceptance criteria collaboratively in a 3 Amigos session to ensure shared understanding
  6. Use Spikes — time-boxed exploratory development to verify feasibility of risky or unclear requirements

Key principle: Requirements must be kept in the problem space (what and why), not prematurely pushed into the solution space (how). The Definition of Ready (DoR) gate ensures requirements are properly refined — including SWA review of architectural impacts — before the team commits in a sprint.

#9. Motivation & Leading without Formal Power

Q: How to motivate people? AMP model?

Leadership without formal power: A software architect has no subordinates — they lead through communication and vision, not orders. Two types of authority:

  • Vested Authority — given by the organization, can be taken away
  • Natural Authority — built through competencies, practice, and personal qualities; portable

How to build Natural Authority (Host Leadership):

  • Lead by example, active listening, share know-how
  • Build relationships, defend the team, let people shine
  • Offer vision through discussion, not dictation
  • Destroy it by: micromanagement, ignoring feedback, forcing solutions, arrogance, blaming the team

Dan Pink's Motivation 3.0 (AMP model):

  • Autonomy — "I manage my own work"
  • Mastery — "I improve in what I do"
  • Purpose — "I know why I do it and it has impact"

Key insight: For creative work, higher extrinsic rewards actually hurt performance (the "hard candle problem").

KAWA diagnostic framework:

  • K (Knowing): Do they know what is expected?
  • A (Able): Do they have the skills?
  • W (Willing): Are they motivated?
  • A (Allowed): Do circumstances allow them to succeed?

Process: Feedback → Active listening → KAWA filter → Check AMP levels → Let them propose their own solution (protects Autonomy) → Agree on next steps.

Moving Motivators exercise: 10 internal motivators (Acceptance, Status, Order, Relatedness, Power, Curiosity, Goal, Honor, Mastery, Freedom). Rank them, simulate a change, see which go up/down — reveals hidden resistance or alignment.

#10. Stakeholder Presentation

Q: Aspects to consider?

Three dimensions:

  1. Content: Clear goal, big picture vs. details, strong arguments (economic advantages, risks, strategic alignment)
  2. Behavior: Eye contact, confidence, response to questions, time management
  3. Visualization: Consistency with spoken word, avoid media conflict, readability

6-step preparation checklist:

  1. Goals — What do I want? (Inform, persuade, get decision, motivate)
  2. Audience — Who is coming? White Knights (allies) vs. Black Knights (skeptics)
  3. Message — USP in one sentence; map advantages, disadvantages, risks, alternatives
  4. Disruptions — Prepare for killer comments
  5. Roles & Resources — Who moderates, presents, takes minutes?
  6. Personal Expression — Active meeting management, "I" statements

Key tools:

  • Marketecture — one-page non-technical system representation (3-5 core areas, core vs. add-on)
  • Elevator Pitch — Problem, Solution, Outcome with clear USP

#3. Architecture Refactoring

Q: What is being done? Which artifacts are affected? Prior experience?

Architecture refactoring changes the internal organization of code into logical layers and components without changing external behavior (interfaces remain the same). The goal is to improve scalability, extensibility, and testability.

Affected artifacts:

  • Code: Structure, dependencies, layering, component boundaries
  • Documentation: Architecture diagrams, deployment views, ADRs, component descriptions must be updated

Levels of change and who decides:

Level What Who decides
Class Code refactoring (local, preserves behavior) Developer — daily work
Component Architectural refactoring Team/PO — Backlog item
Subsystem Architectural refactoring Product/CPO — Epic
System Reengineering or Rewriting Organization/CTO — standalone project

Triggers (Architecture Smells):

  • External signals: Failing builds after commits, new features break other parts, slow deployment, user complaints
  • Internal signals: Cyclic dependencies, duplications, over-generic design

Process to push through with business:

  1. Determine root cause
  2. Define necessary architectural changes
  3. Build a Business Case with quantified ROI
  4. Present to business for approval/budget
  5. Create high-level plan + detailed schedule

Negotiating time: Use Corridors (permanently reserved capacity, e.g., 15% per sprint) or Triggers (automatic response when metrics breach thresholds, e.g., Sonar maintainability index goes red).

Technical Debt Quadrant:

  • Deliberate + Prudent = managed debt with repayment plan
  • Deliberate + Reckless = irresponsibility
  • Inadvertent + Prudent = learning ("now we know how it should have been done")
  • Inadvertent + Reckless = incompetence

#4. Architecture Documentation

Q: Reason and benefit of good documentation? Example?

Documentation is fundamentally communication. It must answer: Why (purpose), Who (stakeholder), and What information they need.

Benefits:

  • Creates shared understanding among stakeholders — without it, everyone has a different mental model
  • Enables informed decision-making — documented trade-offs and rationale prevent repeating past mistakes
  • Guides development — a baseline architecture complete enough to guide but simple enough to communicate
  • Supports onboarding — new team members can understand the system without reverse-engineering it
  • Enables architecture reviews — you cannot review what is not documented

Key frameworks:

  • 4+1+n Views: Use Case, Logical, Process, Implementation, Physical + additional views
  • C4 Model: Context → Container → Component → Code (each level targets different stakeholders)
  • arc42: Popular template providing structure

Example — good documentation helping:

In Flexibility Operation Planning, no view described the end-to-end runtime path of a flexibility request. Each team documented its own service, so every component looked fine in isolation. What was missing was the Process View — the one that makes cross-service timing behavior visible.

Creating the missing E2E runtime view with latency budgets per hop showed that the deadline was exceeded structurally, not because one service was slow. This documentation didn't fix anything technically — it created the shared understanding that unlocked the budget and the decision for architectural refactoring. Picking the view the stakeholder needs, not the one the architect finds interesting — that is the point.

A paper tiger architecture (documentation with no link to reality) creates false confidence.

#1. Systematic Architecture Design

Q: Which methods are known? Practice: Step you struggled with — Domain modelling in Athena

The primary method is the L-Model — systematic workflow from assignment to implementation:

  • Vertical Phase (Analysis): Requirements elicitation, domain model, scenario dynamics, scope & boundaries
  • Horizontal Phase (Design): Conceptual draft, baseline architecture, deployment views, principles & guidelines, increments

The entire L-model is traversed in every iteration — no-op phases are acceptable but never excluded. This is the discipline that prevents erosion.

Architecture = Forces + Creativity + Communication + Decisions. Forces = Requirements + Constraints → defines "Freedom of Choice."

Practice — Domain modelling struggle in Athena:

Athena merges 3 historically separate services (SBOM, VI, PSIRT) into one platform. The domain modelling challenge is extreme: each service evolved its own domain language independently. "Component," "vulnerability," and "asset" mean subtly different things across the three domains.

This is where Event Storming proves essential — it surfaces the actual domain events and forces the teams to confront terminology conflicts in real time. The events discovered become the shared domain model and later define the bounded contexts. Without this, the risk is building a "unified" data model that satisfies nobody.

Conway's Law is directly visible: the organizational separation of 3 teams shaped 3 incompatible domain models. The Inverse Conway Maneuver — deliberately restructuring team communication to match the desired unified architecture — is the strategic response.

#2. Architecture Quality Review

Q: Which qualitative methods and triggers? Where have you done this?

Three qualitative methods: ADR (2 days, focused defect finding), Industry Practice Review (4 weeks, proposes measures), ATAM (2 weeks, trade-off analysis, no measures).

What triggers a review (situations/events): Project phase transitions, architecture drift/erosion detected, architecture smells identified, quality metric thresholds breached, major architectural decisions pending, process gates.

Who initiates (roles): Architect, Enterprise Architect, Process, Developer, QM.

Where done (Enrico's experience):

  • Everything as Code — architecture conformance checking with developers + Enterprise Architect. This is a quantitative approach (Code Quality Assessment) complementing qualitative reviews
  • Athena Architecture at CYS Community Call and Enterprise Architecture Call — presenting architecture for broader review (Industry Practice Review variant)
  • Active Design Review in SWA Training — practiced in both designer and reviewer roles

#3. Architecture Refactoring

Q: What is being done? Which artifacts are affected? Prior experience?

Architecture refactoring changes internal structure without changing external behavior — specifically the integration/interface part of code, while from outside there is no difference. Affected artifacts: Code, Documentation, Integration Tests.

Levels: Class (Developer) → Component (Team/PO) → Subsystem (CPO) → System (CTO).

Enrico's experience — Refactoring and Rewriting:

  1. SVM Monitoring: TinyTiny Reader → Agents — a rewrite of the monitoring data ingestion. The old RSS-reader-based approach was replaced with purpose-built agents. This is system-level change, requiring standalone project approval.

  2. Athena: SBOM decoupling from Mapping — architectural refactoring at the component/subsystem level. The SBOM service had a tight coupling to the mapping functionality. Decoupling required relocating responsibilities, changing dependency direction, and updating integration tests — while preserving the external API contract.

Business case process: Root cause → Define changes → Quantified ROI → Present to business → High-level plan → Detailed schedule. Proactivity pays off — smaller continuous refactorings are easier to sell than massive rewrites.

#4. Architecture Documentation

Q: Reason and benefit? Example of good/bad documentation?

Documentation = communication. Benefits: forces thinking about topics, enables communication, enables feedback.

Good documentation helped (Enrico's example):

  • Used 2 key figures for external communication: the AMEAN loop and 2-loop drawing. These high-level views served as communication instruments for stakeholders who don't need to understand implementation details — exactly the Marketecture / C4 Context level approach.

Bad documentation improved (Enrico's example):

  • Cloud diagram of Vilocify was insufficient. Invited the Ops colleague to review and improve it — demonstrating that documentation must be written from the reader's perspective and validated with the stakeholder who actually uses it. The Ops person needed the Deployment View (Physical View in 4+1) — not the Logical View the developers had been maintaining.

#5. Risk-Based Testing

Q: Approach? Application?

Formula: Priority = Severity x Impact x Effort (variant of RPN = Probability x Impact x Detectability). Related to business risk — testing effort follows business criticality.

Enrico's application:

  • Browser E2E tests — highest-risk user journeys tested end-to-end
  • Defined Ratings — standardized risk classification for consistent assessment
  • Workshop with developers — collaborative risk assessment (3 Amigos approach)
  • Defined amount of needed tests — risk levels mapped to required test coverage density

This follows the 5-step RBT process: Risk Identification (workshop) → Analysis (ratings) → Response (test allocation) → Review → Planning.

#6. Design for Testability

Q: Theory? Where addressed/applied?

Theory: Controllability + Observability + Test frameworks + TDD/BDD.

Where applied (Enrico's experience):

  • Athena: Clear interfaces between services — enabling test doubles and isolated service testing. This is the DFT tactic of loose coupling and Dependency Injection in action.
  • Requirements template: Acceptance criteria guideline — forces Given-When-Then format, ensuring testable requirements from the start (BDD approach to DFT)
  • TDD for core function in Athena PoC — Red-Green-Refactor cycle applied to the core business logic, establishing testability as a first-class architectural concern from day one, not an afterthought

#7. Requirements

Q: Methods to improve? Where applied?

Methods:

  1. Template — SOPHIST/MASTeR structured format eliminates ambiguity
  2. Communication to source — 3 C's, 5 Whys
  3. Visualization — State Diagrams, Sequence Diagrams ("draw what you mean")

Where applied (Enrico's experience):

  • Stay in problem space: Template with User Story sentence + details + Acceptance criteria including risks and "documentation done" + guideline on how to fill them. This keeps the team focused on what is needed, not how to implement it.
  • Feature Spec for bigger items — when a story is too large or complex, escalate to a structured feature specification with architectural considerations and dependencies

#8. NFRs (Non-Functional Requirements)

Q: Top-3 qualities and why? How to obtain?

Quality Business Justification
Availability Business-critical for Siemens — SVM/Vilocify is a core security service
Interoperability Not an e2e solution — many systems consume SVM/Vilocify data; must integrate cleanly
Security Belonging to CYS (Cybersecurity) — must be a role model for the organization

How to obtain:

  1. Service Description including SLAs — formal quality targets
  2. Structured Analysis — Utility Tree, QAW
  3. NFR workshop with Ludwig Mittermeier, ATAM Phase 1 — structured stakeholder workshop for quality scenario elicitation and prioritization

#9. Motivation

Q: How to motivate people? Example — Wolfgang and Athena?

Drive model (AMP): Autonomy, Mastery, Purpose. For creative work, intrinsic motivation outperforms extrinsic rewards.

KAWA diagnostic: Knowing → Able → Willing → Allowed.

Example — motivating Wolfgang to participate in Athena:

  • Diagnosed with KAWA: Wolfgang had knowledge (K) and ability (A), but willingness (W) or circumstances (A) were blocking
  • Applied Drive model:
    • Purpose: Why Athena matters and how Wolfgang's contribution has direct impact
    • Mastery: How participation develops new skills
    • Autonomy: Let Wolfgang choose how to contribute
  • Practical action: Help Wolfgang hand off other responsibilities to free capacity for Athena — addressing the "Allowed" dimension of KAWA

#10. Stakeholder Communication

Q: Which aspects? Explain a situation presenting to non-technical people?

Three dimensions: Content (goal, audience level, arguments), Behavior (confidence, handling questions), Visualization (consistency, readability).

6-step checklist: Goals → Audience → Message (USP) → Disruptions → Roles & Resources → Personal Expression.

Presenting to non-technical people (Enrico's approach): Use the Marketecture approach — simplify the technical architecture into 3-5 understandable areas, show business impact, and present concrete ROI. Management doesn't need to understand microservices — they need to understand "we exceed the business deadline by 40% and no local fix can solve it." Visual instruments (E2E runtime views, AMEAN loop diagrams) become the communication bridge that unlocks budget decisions. The key is selling architecture as a business case — economic advantages, risk reduction, strategic alignment.

#Testing — Different Questions

#Internal and External Quality Attributes

Q: What internal and external quality attributes are you aware of?

The distinction follows the Quality Management Chain (ISO 9126 / ISO 25010):

Process Quality → Internal Quality → External Quality → Quality in Use

Internal quality measures static properties of the software — code, architecture, structure — from a developer's perspective, without running the system:

Level What is measured Examples Tools
Micro (code level) Individual lines/statements Naming conventions, layout, risky constructs, coding standards PC-Lint, QAC, ESLint, IDE plugins
Macro (design level) Class/module design Cohesion, coupling, SOLID principles, design patterns, code duplication Manual peer reviews, SonarQube
Architecture (system level) Layering, component structure, dependencies Absence of cyclic dependencies, dependency direction, layer isolation Axivion, Sotograph, Structure101, ArchUnit

Key internal attributes: Maintainability, Analyzability, Modifiability, Reusability, Testability.

External quality measures dynamic behavior while the system is running — from the user's perspective:

Attribute What it means
Functionality Does it do what the user needs? (correctness, completeness, appropriateness)
Reliability Does it keep working? (fault tolerance, recoverability, availability)
Performance / Efficiency Is it fast enough? (time behaviour, resource utilization, capacity)
Usability Can the user operate it? (learnability, operability, error protection)
Security Is it protected? (confidentiality, integrity, authentication, non-repudiation)
Compatibility / Interoperability Does it work with other systems?

The critical relationship: Internal quality is the hidden root of external behavior. Poor internal quality (e.g., cyclic dependencies, God classes) inevitably degrades external quality over time — even if the system appears to work today.

FURPS+ model as an alternative classification: Functionality, Usability, Reliability, Performance, Supportability — plus constraints (design, implementation, interface, physical).

Key principle: "Quality cannot be tested into software at the end." It must be built in from the start through architecture, design, and continuous quality management.

#Writing Test Cases for Quality Attributes

Q: How do you write test cases to support these quality attributes?

The bridge from quality attribute to test case is the Quality Attribute Scenario — a 6-part template that turns vague NFRs into testable specifications:

Element Purpose Example (Availability)
Source Who/what triggers the stimulus Internal monitoring system
Stimulus The event or condition Server node crashes
Artifact What is affected Order processing service
Environment Under what conditions Normal operation, peak load
Response Expected system behavior Failover to backup node, no data loss
Response Measure Measurable acceptance criterion Recovery within 30 seconds, 99.95% uptime per month

Without a Response Measure, objective test evaluation (Pass/Fail) is impossible. This is the single most important element — it turns a wish into a test.

Process to derive test cases from quality attributes:

  1. Identify quality attributes — use ISO 25010, FURPS+, or stakeholder workshops (QAW)
  2. Prioritize — Utility Tree ranks scenarios by Business Value × Architectural Risk (H/M/L)
  3. Write Quality Attribute Scenarios — 6-part template for each high-priority attribute
  4. Derive test conditions — the Response Measure becomes the acceptance criterion
  5. Select test design technique appropriate to the attribute type:
Quality Attribute Test Approach Technique
Performance Load/stress testing Measure response time under defined load profiles
Reliability / Availability Fault injection, failover testing Chaos engineering, kill processes, measure recovery time
Security Penetration testing, static analysis OWASP testing guide, SAST/DAST
Maintainability Static analysis, architecture conformance SonarQube metrics, ArchUnit rules, cyclomatic complexity
Usability User testing, heuristic evaluation Task completion rate, error rate, time-on-task
Interoperability Integration testing Contract testing (Pact), API conformance

For internal quality attributes (maintainability, testability, analyzability): test cases are primarily automated quality gates in the CI/CD pipeline — SonarQube thresholds, ArchUnit conformance rules, coverage minimums. These run continuously, not as one-off test campaigns.

For external quality attributes (performance, reliability, security): test cases follow the classic stimulus → response → measure pattern from the Quality Attribute Scenario. Each scenario directly becomes one or more test cases with explicit pass/fail criteria.

Key insight: The Utility Tree determines which quality attributes get the deepest test coverage. H/H scenarios (high business value, high architectural risk) get the most test investment — this connects directly to Risk-Based Testing.

#Hypothetical Scenario Questions

Q: What if your domain expert has left the company? How would you gather information about the existing system?

This is a reverse engineering situation — reconstructing architectural knowledge when the primary source is gone:

  1. Code as the single source of truth:

    • Static analysis tools (Axivion, Sotograph, Structure101) to extract the actual architecture from code — dependencies, layers, component boundaries
    • Architecture conformance checking to compare code reality against any existing documentation

  2. Documentation archaeology:

    • ADRs (Architecture Decision Records) — if they exist, they capture the why behind decisions, which is the hardest knowledge to reconstruct
    • Git history and commit messages — git log and git blame reveal the evolution of decisions
    • Wiki pages, Confluence, old presentations — even outdated docs reveal intent

  3. People who remain:

    • Developers who worked alongside the domain expert — they absorbed knowledge through osmosis
    • Operations/DevOps — they know the runtime behavior, deployment topology, and failure modes
    • Product Owner / Business stakeholders — they know the why even if not the how

  4. The system itself:

    • Event Storming with the remaining team — reconstruct the domain model from what the system actually does
    • Runtime observation — logs, metrics, traces reveal actual behavior and integration points
    • Test suites — existing tests document expected behavior (if they exist)

  5. Structured recovery:

    • Conduct an Industry Practice Review — experienced external reviewers interview remaining team members and analyze the architecture
    • Build a C4 Context and Container diagram from what you discover — this creates the missing shared understanding

Key principle: This scenario highlights why documentation is communication and why the architect must ensure knowledge is not trapped in one person's head. Conway's Law applies to knowledge too — if only one person understands a domain, losing that person creates an architectural blind spot.

#Interview Tips from This Participant

Key takeaway: Be prepared for follow-up pressure. The assessors will:

  • Say "I am not happy with that answer" to push you deeper
