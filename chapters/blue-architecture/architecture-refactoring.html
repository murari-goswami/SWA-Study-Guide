🔵 Architecture refactoring (re-engineering, re-writing)

#What it is and why to do it

  • Integral part of design: Architectural refactoring is not just a patch after development, but a direct part of architecture creation itself. It functions as a continuous feedback loop (Refine & Assess -> Refactor) for improving the executable increment.
  • Goal and impact: Architectural refactoring does not change external behavior (interfaces remain the same), but changes the organization of code into logical layers and components.
    • The goal is to improve scalability, extensibility and testability of the system.
  • Triggers (Triggers and Smells): Besides regular iterative maintenance, refactoring is triggered based on external stimuli and symptoms:
    • Response to Lehman's 2nd Law (system complexity naturally grows, without intervention inevitable "design erosion" threatens).
    • Identification of specific symptoms = Architecture Smells
      • External signals: Failing builds after every commit, new feature breaks other parts, slow deployment, user complaints about performance.
      • Internal signals: Cyclic dependencies (solved e.g. by dependency injection or entity relocation), duplications, strict centralization or unnecessarily over-generic design. "Smell" is just an indicator of a possible problem, not proof.

#Levels of changes and who decides about them

  • Class: Code refactoring
    • Local impacts, changes structure, preserves behavior. It is cheaper and ideally done continuously as part of daily work.
    • solved by developer as part of daily work or regular iterations (Task).
  • Component: Architectural refactoring
    • solved by Team/PO through Backlog item.
  • Subsystem: Architectural refactoring
    • solved by Product/CPO as Epic.
  • System:
    • solved by Organization/CTO as massive standalone Project. Reengineering System-wide impact. Means taking apart the system (reverse engineering) and rebuilding it (forward engineering). Requires standalone project. Rewriting Throwing away the old and writing completely new code. Comes into play when neither refactoring nor reengineering is enough. Affects all system qualities, but is extremely costly and risky.

#Process of pushing through with business

  • It is not just a technical task, it is mainly about selling the idea to management. You must create a strong Business Case and show business value to justify the costs.
  • Steps:
    1. Determine the exact root cause of the problem.
    2. Define necessary architectural changes for correction.
    3. Build a Business Case with clearly quantified ROI (savings in money/time/risks).
    4. Present to business for official approval and obtaining budget.
    5. Create a high-level plan.
    6. Assemble a detailed schedule with estimates and resource allocation.
  • Proactivity pays off – selling smaller continuous refactorings is much easier than asking for money for massive rewrite.

#How to negotiate time for maintenance

  • Corridors: Permanently reserved capacity (e.g., 15% of time in each sprint, or every 6th sprint is purely cleanup).
  • Triggers: Automatic response to exceeding limits (e.g., maintainability index in Sonar drops into red zone, CI/CD pipeline takes over 20 minutes).

#Technical debt

Financial metaphor: you take a loan (quick delivery of feature to market), pay interest (more expensive and slower maintenance of bad code), debt repayment is performing refactoring.

Technical debt quadrant:

  • Deliberate + Prudent (Managed debt): Intentional risk to meet business goal, with clear plan and awareness that it must be rewritten soon.
  • Deliberate + Reckless (Irresponsibility): "I don't care about design now, just deliver it and we'll see.".
  • Inadvertent + Reckless (Incompetence): Team creates debt from ignorance of architectural principles.
  • Inadvertent + Prudent (Learning): "Aha, we now know how it should have been done correctly, let's fix it.".

Debt must be systematically measured (static analysis, drops in velocity, density of necessary changes in one component) and transparently published.

#Practice: Application of refactoring theory to historical projects

1. Flex Operation Planning — cyclic dependency between measurement and violation services

  • Smell (internal signal): A forecasted measurement was consumed by two services — one presenting it in the UI, one detecting violations. The violation service also had to read the actual measurement back from the measurement repository, which closed a cyclic dependency between the two components. Symptom: unpredictable, flaky end-to-end tests.
  • My action: I identified the cycle as the root cause (not the tests), introduced continuous polling as a deliberate short-term workaround to stabilise delivery, and documented that it is not the target solution. The real fix (breaking the cycle via dependency inversion / event-driven hand-over) was sized, prioritised together with the Product Owner and put on the backlog.
  • Planning level: Component → Backlog item (architectural refactoring owned by Team + PO).
  • Technical debt quadrant: The polling workaround is Deliberate + Prudent — conscious debt, with an explicit repayment plan and a backlog item behind it.
  • Process: Steps 1–2 (root cause, required change) plus explicit prioritisation with the PO — proactive, small, sellable refactoring instead of waiting for a rewrite.

2. Case expiry — from UI-driven check to TTL-based expiry (Valkey)

  • Smell: No central orchestration for the rule "a case expires after 24 hours". The first solution was UI-driven: whenever the UI opened a case, the API checked the age and only then flipped the state to expired. The business state therefore existed only if somebody looked at it — the trigger lived in the wrong place.
  • My action: Moved the lifecycle out of the UI into the platform. Cases are held in an in-memory store (Valkey) with a TTL; TTL expiry itself emits the event that expires the case. The state becomes correct by construction, independent of any user interaction.
  • Planning level: Component/Subsystem — a backlog item that changed the state ownership, not the external contract (behaviour preserved, organisation changed).
  • Technical debt quadrant: The original UI-driven check was Inadvertent + Prudent — once we understood that a lifecycle rule must not depend on a UI trigger, we corrected it.
  • Lesson: An architecture smell is often not "ugly code" but a trigger sitting in the wrong component. Fixing ownership of the trigger removed a whole class of inconsistent-state defects.
