Domain-Driven Design (DDD)

#Philosophy & Strategic Design (The "Why" and "What")

  • Motivation:
    • The greatest complexity of software systems often does not stem from technologies, but from the business domain itself. DDD helps manage this complexity and avoid the so-called "Anemic models".
  • Ubiquitous Language:
    • A common, strict language used by both developers and business experts. It must be consistently used in spoken language, in diagrams and directly in source code.
  • Subdomains (Core, Generic, Supporting):
    • Added from practice: Division of business into
      • Core domain (main company value, we deploy full DDD)
      • Supporting domain (support activities, simple code is enough)
      • Generic domain (common things like accounting that can be bought ready-made)
  • Bounded Contexts:
    • Models are valid only in a specific context. A term (e.g., "Aisle" or "Order") can mean something completely different for a warehouse worker and something else for billing.
    • DDD advises avoiding attempts to create one huge unified model and instead managing diversity.
  • Context Maps:
    • An informal diagram that shows Bounded Contexts (teams) and maps their social and technical interactions.
  • Co-operation patterns: *
    • Shared Kernel:
      • Two contexts share a common model and code, changes occur strictly based on agreement of both teams.
    • Conformist:
      • A team unconditionally adopts and uses another team's model because building a mapping layer would be too expensive.
    • Anti-corruption Layer (ACL):
      • All concepts of one context are explicitly mapped to another through an isolated layer to prevent the spread of "infection" and ripple effects when foreign models change.

#Discovery

  • Event Storming: "Low-tech" workshop and visual technique for discussion with domain experts. It serves to understand the dynamics of domain processes and gain the overall "Big Picture".
  • Cards and dynamics: Participants gradually stick colored notes on the wall:
    • Domain Event (orange): What happened in the past (e.g., "Delivery arrived").
    • Action / Command (blue): Command that triggers the event.
    • Actor / User (yellow/green): Who triggers the command.
    • Policy (purple): Rule responding to an event (e.g., "Whenever X happens, do Y").

#3. Tactical Design (The "How")

Tactical patterns help transform abstract domain models into a computer program where we must deal with memory, multiple users and databases.

  • Domain-centric Architecture: The domain model is at the very center of the architecture. Hexagonal architecture (Ports and Adapters) fits perfectly for this.
  • Anemic vs. Rich models: * Anemic model: Contains only data (getters/setters) and associations, all logic is scattered elsewhere. For complex systems, this is an anti-pattern.
    • Rich model: Enriched model that directly encapsulates domain behavior and complex operations (e.g., void GeneratePicks()).
  • DDD Tactical Patterns:
    • Entity: An object that has a unique identity independent of attributes and changes over time (has a lifecycle).
    • Value Object: Structured data without its own identity (e.g., address or amount). They are "immutable" – operations on them do not modify state, but return a new object.
    • Aggregate: A group of Entities and Value objects forming a consistency boundary. From the outside, the aggregate is manipulated only through its main entity (Aggregate Root). It ensures absolute consistency within its boundaries; relationships between different aggregates are then often only "eventually consistent".
    • Repository: Abstraction over data storage. It works fundamentally at the level of entire Aggregates (loads and saves them as a whole).
    • Factory: A factory that encapsulates complex logic for creating new, fully valid and consistent Aggregates.

#4. Deep Dive: Architectural details and Trade-offs

#Conway's Law and its influence on Bounded Contexts

Architecture is not just about technologies, but about people. Conway's Law applies here: "Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations."

  • In DDD, this means that Bounded Contexts and the division of the domain model must mirror the team structure.
  • It is not possible to have one unified model on which 3 different departments work (e.g., Nuremberg, Stuttgart, Pune) without constant conflicts.

#Aggregate Design: Consistency vs. Concurrency

Aggregate design is always about finding a trade-off between data consistency and the possibility of concurrent processing:

  • Large aggregate (Design for Consistency): The Order aggregate contains both Position and Pick. It can guarantee strict rules (e.g., never pick more items than are in the order). The price for this is that it blocks concurrency – the system cannot process multiple "Picks" from one order in parallel.
  • Small aggregates (Design for Concurrency): Order and Pick are two separate aggregates, so-called Aggregate Roots. This allows parallel processing, but we lose immediate consistency – the system must rely on so-called Eventual Consistency across aggregates, often through an Event Bus.

#Entity vs. Value Object (Detailed comparison)

Detailed differences in implementation:

  • Identity: Entity has a special ID; Value Object is identified by the value of ALL its properties.
  • State change: Entity is Mutable (can be changed); Value Object is Immutable (cannot be changed, methods always return a new object).
  • Lifecycle: Entity has one; Value Object does not.

#Layer Dependencies in DDD

Unlike classic 3-tier architecture (UI -> Business -> Data), DDD Layered/Hexagonal Architecture has a completely reversed direction of dependencies for infrastructure:

  • Domain Layer is absolutely clean, does not depend on ANY other layer. It defines Entities, Aggregates and interfaces of Repositories.
  • Application Layer depends on Domain Layer (coordinates objects, manages transactions).
  • Infrastructure Layer (database, cache) DEPENDS on Domain Layer. It implements Repository interfaces defined in the domain, often using Dependency Injection.
