🔵 Goals-Principles-Decisions (GPD) Model

#Description of the technique

GPD is a cascading model (often following a specific requirement - Req) that connects the assignment with the technical solution. It forms a logical chain:

  • Goals: What we primarily want to achieve (for example consistency, usability, reusability).

  • Principles: General rules and boundaries derived from goals (for example validation as early as possible in the UI, business logic only in the BL layer).

  • Decisions: A specific implementation step that fulfills a principle (for example email validation on every key press, prohibition of logic in RestAPI).

#Why use this technique (Benefits)

It ensures traceability and logical justification of architectural decisions. Every decision has a clear rationale - it does not originate from personal preferences, but can be traced back through an agreed principle to the original goal.

#Examples from practice - from study materials

  • Registration - Email syntax:

    • Req: Email syntax must be correct.
    • Goal: Correctness, Usability.
    • Principle: Validate syntax at input as early as possible in the UI layer.
    • Decision: Validate the syntax of the email field on every key press in the UI.

  • Registration - Unique Nickname:

    • Req: Nickname must be unique.
    • Goal: Consistency, Correctness.
    • Principle: Uniqueness validation is performed in Business Logic (BL).
    • Decision: Validate uniqueness only after pressing the "Register" button.

  • API Architecture:

    • Goal: Reusability, Maintainability, Flexibility.
    • Principle: BL implementation belongs ONLY to the business layer.
    • Decision: No business logic in the RestAPI layer.

  • Tribe-Blue Feedback:

    • Req: Provide a standardized environment for all teams for feedback.
    • Goal: Obtain feedback from all teams.
    • Principle: Accept information in a structured way.
    • Decision: Use a Wiki template as the method.

#Example from practice - decision within Unit multiplier in the system

Situation: In NGM every process value is a physical quantity (50 kV = value 50 + multiplier k + unit V). Components hard-coded unit and multiplier, and the assumptions were not in sync across the processing chain — negotiated developer-to-developer, undocumented. Mismatches are only found when test-driving the code, and in grid operation a wrong multiplier can lead to wrong decisions on the electrical grid.

  • Req: One unambiguous, system-wide standard for unit multipliers.
  • Goal: Correctness and Consistency of physical values, Maintainability (less know-how needed to change code), Independence from external model changes.
  • Principles:
    • A physical quantity is never a bare number — use the CIM electricity data type (value + unit + multiplier, IEC 61970-301) as the attribute type.
    • NGM defines one fixed unit/multiplier per data type (e.g. ApparentPower always MVA); internal APIs rely on it and therefore don't transport it at runtime.
    • Convert only at the system boundary — 3rd parties convert to/from the NGM standard; internal processing never converts.
  • Decisions:
    • Unit and multiplier are part of every API/profile specification, so each API definition is self-contained.
    • For measurements/controls, drop unitMultiplier + unitSymbol and replace them with a single measurementValueType attribute driven by a new NGM enum of electricity data types — a conscious, documented deviation from CIM.
    • Maintain a central table of the agreed multiplier per data type as the single source of truth.

Concrete example — TransformerEnd.ratedS (apparent power):

Before After
Type plain double ratedS ApparentPower (value + unit VA + multiplier M)
Unit/multiplier hard-coded per component, kVA in one service, MVA in the next fixed by NGM: always MVA
Internal API payload number only — meaning implied electricity data type; unit/multiplier known from the spec, not sent at runtime
3rd-party integration each team guesses converts to/from the NGM standard at the boundary

Same for measurements: instead of a measurement carrying unitMultiplier = "k" + unitSymbol = "V", it carries measurementValueType = Voltage, and any component can look up that Voltage is always kV.

Why it matters (GPD value): The chain makes the decision defensible instead of personal preference — and when domain experts challenged the chosen multipliers (base units vs. kV/kW/kVA/kVAr for MV/LV grids), the discussion could be held at the level of the principle, with the decision re-opened without touching the goal. That is exactly the traceability GPD is for.
