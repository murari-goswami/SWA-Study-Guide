🔵 Architecture Decision Records (ADR)

What it is and why we need it

An ADR is a short text record (typically in Markdown) that captures a single significant architectural decision. It addresses the main problem of classical documentation — the loss of context (architectural amnesia). It prevents future developers from either blindly accepting old decisions or dangerously changing them without knowing the original rationale.

#Key attributes

When introducing ADRs, the following questions must be answered:

  • What? (What exactly are we deciding)
  • How? (What format will we use and where will it be stored — ideally directly alongside the code)
  • Where? (Where is the boundary of validity of the decision)
  • How much? (Level of detail — an ADR should be 1 to 2 pages long)
  • Difficulties? (What pitfalls and risks are associated with it)

#Standard structure (Michael Nygard, 2011)

  1. Title: A short name (e.g., "ADR 1: Migration to PostgreSQL").
  2. Context: A neutral description of the situation, forces, and facts that drive us towards a solution.
  3. Decision: The actual decision (active sentences, "We will...").
  4. Status: The state (Proposed, Accepted, Superseded).
  5. Consequences: The consequences of the decision (positive and negative future impacts).

#SWA responsibilities in relation to ADR

The Software Architect (SWA) bears direct responsibility for ensuring that key decisions do not remain only in the heads of developers or in meeting notes. Their main tasks include:

  • Documenting taken decisions: The SWA must ensure that every architecturally significant decision is formally captured.
  • Ensuring consistency: The architect is responsible for ensuring that new decisions (ADRs) do not contradict existing architectural views and principles.
  • Regular review: The SWA must regularly check and revise the state of documentation and decisions so that they reflect the current reality of the system.
  • Defining the process: The SWA determines what will be documented, in what format, and where the records will be stored.

#Templates

  • arc42 has no special ADR template, but the ARCH documentation template contains an Architectural Decisions section where links to ADRs stored in the repository (e.g., as MD files) can be placed.
  • A range of templates available online (Henderson)
  • The classic Nygard (2011) template — simple
  • MADR (Markdown Any Decision Record) — a modern, open-source standard. Compared to the classic version, it adds Considered Options and Pros/Cons.

#MADR structure (the template used in practice)

MADR is the de-facto standard when an organization needs comparable decisions, not just recorded ones. Nygard answers "what did we decide and why"; MADR additionally answers "what else did we evaluate and why did we reject it" — which is exactly the information an architecture review or a later reversal needs.

Section Purpose
Title Short, solution-oriented phrase ("Use Kafka for inter-service eventing").
Status Proposed / Accepted / Rejected / Deprecated / Superseded by ADR-XXX.
Context and Problem Statement The situation and the question being answered, neutrally phrased.
Decision Drivers The forces: quality attributes, constraints, compliance, cost, skills. These are the criteria the options are judged against.
Considered Options The realistic alternatives, including "do nothing".
Decision Outcome The chosen option and the justification against the drivers.
Positive Consequences What improves (which quality attribute is gained).
Negative Consequences The accepted trade-off, risk, or new debt.
Pros and Cons of the Options Per-option evaluation — the audit trail of the reasoning.
Links Related ADRs, requirements, superseded/superseding records, spikes, PoCs.

The decision drivers are the hinge of the whole template: they turn an opinion into a traceable evaluation, and they are the first thing to re-read when someone asks "can we reverse this now?"

#Process operation (Practice)

  • Who writes it: The topic owner (developer, tech lead). It does not always have to be the architect who writes it, but the SWA (Software Architect) bears responsibility for ensuring the decision is formally captured ("Documents taken decisions").
  • Who approves it: An architecture committee (board), lead architect, or affected stakeholders (depending on how large an impact the decision has).
  • How it is communicated: Discussion and review of the proposal typically take place via Pull Requests. Once approved, the final ADR is published (e.g., via an automated build from Git to an internal portal) so that it is readable for the entire organization.
  • Who maintains it: The development team. The documentation is versioned directly alongside the source code (Docs as Code). When the architecture changes, old ADRs are not deleted — their status is simply updated to "Superseded" and a link to the new decision is added.

#Real-world example: Turning ADRs into an Architecture Fitness Function

#Situation

Our NGM group already had an ADR culture: the MADR template, a review process, and the wiki as source of truth. I authored ADRs for my product area and evaluated those drafted by teammates. The process worked — the scale did not. Past 110 ADRs:

  • Nobody could find the right decision (wiki keyword search ≠ knowing the title).
  • Nothing verified that the code still obeyed it (e.g., our Kafka topic naming convention).
  • Teams started seeing ADRs as bureaucracy.

#My actions (Applying the theory)

I treated ADRs as executable constraints, not documentation:

  • Wiki → Markdown in the repo (Docs as Code), same MADR template, versioned next to the code.
  • Pull Request per decision — review on the PR, merge = approval, git log = decision history, supersession is traceable.
  • Indexed all ADRs into the NGM context ("engine brain") so they are findable in natural language ("how do we name Kafka topics?") instead of by title.
  • ADRs loaded into the agent's context before coding — the decision shapes the code at authoring time.
  • Validation as a fitness function: the agent checks source code against the applicable ADRs and reports violations with a link back to the deciding record.

#Evaluation and lessons learned

  • A decision that cannot be found does not exist — past ~50 records, retrieval is the bottleneck, not authoring.
  • An unverified decision degrades into an opinion — automate the check where the rule is machine-checkable (naming, layering, dependencies); the rest stays context for humans and agents.
  • Adoption follows value, not mandate: ADRs stopped being "extra bureaucracy" once they instantly answered "why is it designed this way?".
