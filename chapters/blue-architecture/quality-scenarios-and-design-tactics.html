🔵 Quality scenarios and Design Tactics

#Summary / Introduction

Quality attributes (such as performance, security, or modifiability) often affect architecture more than functional requirements. The key problem is that we cannot prioritize, implement, or test quality requirements unless we can describe them in detail. That is what "Quality Scenarios" are for. Once a scenario is clearly defined and prioritized, we select suitable "Design Tactics" - sets of proven architectural approaches.

#Quality Scenarios and their prioritization

  • Scenario structure: Each scenario must contain exactly six elements:

    1. Source: Who or what triggers the stimulus (e.g., end user, unauthorized attacker).
    2. Stimulus: What exactly happens (e.g., attempt to access data, incoming events).
    3. Artifact: Which part of the system it affects (e.g., the whole system, database, UI).
    4. Environment: Under what conditions it happens (e.g., normal operation, overload mode, under a DDoS attack).
    5. Response: How the system should react (e.g., block access, create an audit trail).
    6. Response Measure: A clear, measurable success metric (e.g., response within 5 minutes, zero data loss).

    Utility Tree: A key tool to select the most important quality scenario from many. Scenarios are evaluated on two axes (Business Value and Architectural Impact) and those rated High/High are prioritized (so-called Architecture Significant Requirements).

    • Root: Represents overall system "utility" (quality).
    • First level: Main quality domains (Performance, Security, Modifiability...).
    • Second level: More specific refinement (e.g., Performance splits into Latency and Throughput).
    • Leaves: The concrete, measurable Quality Scenarios (e.g., your NAMUR case with 5 kHz).

    Prioritization: Each leaf scenario gets two values (e.g., High / Medium / Low):

    • Business Value (How important it is for product success for the customer).
    • Architectural Impact / Risk (How complex and risky it is to build into the architecture).

    The architect then takes the High/High scenarios and makes them the top priority for design.

#Design Tactics (Tactic catalogs)

Tactics are grouped by the specific quality domain they address:

  • Fault Tolerance:
    • Detection (Ping/echo, Heartbeat).
    • Preparation and recovery (Active/passive redundancy).
    • Reintroduction (Rollback, State resynchronization).
    • Prevention (Transactions, Removal from service).
  • Security:
    • Resist attacks (Authenticate/Authorize users, Limit access).
    • Detection (Intrusion detection).
    • Recovery (Audit Trail).
  • Performance:
    • Resource demand (Manage event rate, Reduce overhead).
    • Resource management (Introduce concurrency, maintain multiple copies).
    • Resource arbitration (Scheduling policy).
  • Modifiability:
    • Localize changes (Semantic coherence).
    • Prevent ripple effects (Hide information, Use an intermediary).
    • Delay binding time (Polymorphism, Configuration files).
  • Robustness:
    • A deeper look at what happens when a fault arrives. Focuses on detecting faults, recovering from them, and preventing them.

#Design strategies - How to address the most important quality

Design Tactics are individual building blocks (e.g., "add caching", "use active redundancy"), while a Design Strategy is the overall plan for how to satisfy the most important quality scenario.

  • Pattern selection: take critical scenarios (High/High) and choose an Architectural Pattern (e.g., Microservices, Event-Driven, Layered) that naturally supports the required tactics.

  • Trade-off management: improving one quality often makes another worse. The strategy must balance these trade-offs (e.g., heavy encryption for Security hurts Performance, so also plan for additional hardware resources).

#Practice (Flex OP — Scalability of the congestion interface)

Quality attribute: Scalability — the number of congested equipment (EQ) items in one congestion case is data-driven, not design-driven.

#Quality scenario (six elements)

Element Content
Source Congestion Prediction service
Stimulus Congestion case EQ count scales from ~10 to 10,000+ (≈80 % of the grid congested)
Artifact The interface between Congestion Prediction and Congestion Prevention
Environment Peak congestion / unhappy path — widespread grid congestion
Response The payload is bounded: the event stays small and the detail data is fetched in throttled batches
Response Measure Kafka message size stays bounded regardless of EQ count; no single operation carries the full data volume

Prioritisation: High business value (grid stability) + High architectural impact (structural ceiling of Kafka) → an Architecture Significant Requirement.

#Design tactic: Claim-Check with batched deferred resolution

Pattern: split the domain event into a lightweight claim (published via Kafka) and a separately queryable detail set (fetched via batched REST).

  1. Congestion Prediction publishes CongestionPredicted { caseId, eqIds[] } — identifiers only, no P/Q values — on topic siemens-gsw.congestion-prediction.congestion-predicted.1. The payload grows linearly with EQ count but stays small (IDs are cheap).
  2. Congestion Prevention consumes the event and resolves the P/Q values through a batched query endpoint: GET /V1/predicted-measurement/{caseMrId}/equipmentMrids/startTime/endTime/.
  3. Batch size is bounded — each batch returns a fixed maximum number of EQ details. Normal cases need 1–2 batches; extreme cases simply run more batches sequentially without breaking anything.
Problem How the tactic answers it
Kafka max payload The event carries only IDs — message size stays bounded regardless of EQ count
Linear growth of EQ count Batching absorbs growth — more EQ means more batches, not bigger messages
System blocking No single operation carries the full data volume; work is split into bounded chunks

#Scope — what the tactic deliberately does not do

  • It does not make anything faster — this is a scalability tactic, not a performance tactic.
  • It does not handle Kafka outages or service crashes — that is resilience, a separate concern.
  • It does not retry or circuit-break — those would be later resilience additions if needed.

#Trade-off

Congestion Prevention now depends on a synchronous query to obtain the P/Q values, which adds latency and a runtime dependency on the prediction side. This is accepted consciously: the alternative — putting everything into the Kafka message — has a hard structural ceiling that cannot be engineered around. A bounded latency cost is traded for an unbounded size risk.
