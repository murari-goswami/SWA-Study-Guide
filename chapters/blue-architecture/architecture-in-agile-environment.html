🔵 Architecture in Agile Environment

#Summary / Introduction

The core of agile architecture is to build a system that is clean, simple, flexible, and able to evolve continuously. Unlike the classic approach, the main goal is to enable fast changes and rapid deployment, so the system must stay deployable and verifiable at any time during a sprint.

We do not achieve this with complex designs, but by keeping strict priorities: simplicity before generality, hard-coded solutions over excessive configuration, and working code over premature optimization. Architecture is not made by a single person at a desk - the team that builds the system also designs it.

A key skill of an agile architect is to defer decisions until there is enough knowledge to make them safely, while avoiding "dead-ends" that block future adaptability. The team must also watch for "architecture smells" such as too much abstraction, futuristic architecture that solves non-existing problems, or "paper architecture" that looks great in UML diagrams but has no link to real code.

#Classical x Agile architect

  • Classical - architecture is done upfront, detailed, binding, ivory-style, waterfall.
  • Agile - architecture is created as a shared team effort, iteratively, while keeping the vision.

#DoD - definition of done

Distinguish developer "Done" from real Done (tested, documented, passes CI/CD, integration tests ok).

#DoD bloating - countermeasures

  • Automate.
  • Use a checklist that references external procedures.
  • Split it (different for Story, Sprint, Release).
  • Keep it lean and prune it.

#Architectural Runway (Lead time)

  • Architecture as a background task, leading development by 1-2 sprints. In a sprint, we implement what was designed or explored in the previous sprint.

#Spikes (Research tasks)

  • A research task where the goal is not delivery, but learning. Used for "deep probes".

#Enablers vs. User Stories

  • An enabler is work that enables future development (laying foundations). In practice it extends the "Runway" = creates lead time. This work should be separated, not hidden inside normal user stories. Otherwise it is managed like standard tasks. Enablers can result in NFRs.

#Enablers - types

  • Exploration - explores and gains knowledge.
  • Architectural - implementation of architectural stories (e.g., a new core skeleton).
  • Infrastructure - bring up the pipeline.
  • Compliance - formalities, audit preparation.

#Definition of Done (DoD) for Architecture

A decision is:

  • done
  • documented (ADR)
  • communicated (the team understands)
  • validated as feasible (PoC is OK)

#NFR in Agile - overview

  • Split into categories - Story-like, Constraining, Cross-cutting.

#NFR - Story-like (example: redundancy switches)

  • Describe as a user story and deliver within a sprint as a standard task.

#NFR - Constraining (example: search speed)

  • Include in acceptance criteria of the given user story - search works and is fast.

#NFR - Cross-cutting

  • In architecture with lead time, do a spike, validate the principle, create a pattern/example, and include it in DoD at the right level.

#Architecture work in backlog

  • Done by the team, provides value, needs resources - allocated like normal backlog work, groomed (breakdown, thinking, estimates).

#Architecture owner

  • Normally done by the agile team, but the outside world needs one contact. So the team has one representative (architecture owner) - represents, coaches. The team still does and decides architecture. It is a part-time role - a normal team member who codes, but spends part of the time communicating.

#Two system metaphor

  • System1 = the technical solution itself.
  • System2 = organization, company, processes, bureaucracy, constraints (big impact, see Conway's law).

The architect must keep the value stream in shape, i.e., care for both systems. Fearless Journey - a board game, helps identify obstacles in System2.

#Decide at last reasonable moment

  • Too early = BDUF and a wrong decision can be locked in; too late = the team is blocked. The architect tracks it, but decides when they have the most knowledge while not blocking the team.

#Tiger Teams - conquer and divide

  • The most experienced developers and architects do the exploration, prepare the path, practices, and test technologies (conquer). Then instead of handing over via presentations/wiki, they split up and work inside the teams to make it real.

#Travellers

  • Nomads who rotate between teams per sprint, spread know-how. During their stay they are full team members, doing coaching, pair programming, whiteboard workshops, learning lessons.

#Design / SAD (System Architecture Documentation) workshops

  • Design - every sprint in each team, at the whiteboard, light UML, not for documentation.
  • SAD - mainly at the end of the tiger phase, document the solution and help spread it; later it can be updated.

#Component owners

  • Shared code - everyone can contribute, but there is a designated architecture guarantor. Does not block commits (no bottleneck), does not slow development, but improves the solution with the author afterwards to keep the component healthy.

#Real-world example – CRR - No Big up front design

This case study shows how easy it is to slip into "architecture smells" and Big Design Up Front (BDUF).

  • Context: In the Flex targt arch CRR - we agree to have feature parity and make first no up front design but a happy path based flow.

  • Problem (The Smell):

    • Rather than focussin on big upfront design on CRR, with many unknown and validation. WEe agree to do incremental design iteration and validation and proceed with the agile way.

  • Agile Retrospective and Lessons Learned:

    • The principle of Simplicity before generality was violated: Instead of an upfront "bulletproof" solution, a simple baseline (happy path) should have been built first. But we make sure the happy paths are good in quality as well.
    • We violated Decide at the last reasonable moment:
      • Use of ACL wherever required.
