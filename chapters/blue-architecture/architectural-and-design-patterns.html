🔵 Architectural and Design Patterns

#Summary / Introduction

Patterns are proven and reusable solutions to commonly recurring problems in software design. The main idea is not to reinvent the wheel, but to use a time-tested and standardized approach. Although the terms Design Pattern and Architectural Pattern are often used separately, their fundamental principle is the same and they differ primarily in their scope and level of abstraction. All patterns are standardly documented using the so-called "Pattern language" so that every developer can easily understand them.

#Documentation and structure of patterns (Pattern Language)

  • Documentation structure: Each pattern should be described using a specific template.

    • problem and context definition
    • solution structure
    • behavior (dynamics)
    • subsequent consequences (Benefits and Liabilities / Trade-offs).

  • Application in practice: The developer analyzes the problem, looks in the pattern catalog, selects an appropriate pattern, adapts it to their context and implements it.

#How to correctly select a Pattern (5 steps)

The selection must not be done blindly, but strictly systematically through 5 clear steps:

  1. Identify The Problem:

    • It is necessary to precisely analyze the nature of the problem, solution requirements and constraints.

  2. Check For Available Patterns:

    • Based on the pattern catalog, narrow down the vast number of existing patterns to a handful of those that fall into the same domain as the problem being solved.

  3. Analyze Available Patterns (Benefits):

    • Compare the requirements of our system with the specific benefits and forces that the considered patterns bring.

  4. Analyze Available Patterns (Liabilities):

    • Evaluate the disadvantages (liabilities) of the selected patterns. If a pattern brings a disadvantage that is critical for the system and cannot be satisfactorily solved, we must discard it.

  5. Select A Pattern:

    • From those that passed the filter, we always choose the absolutely simplest pattern that will serve its purpose (The simplest pattern that possibly could work).

#Architectural Patterns and their Scope

While classic (Design) patterns solve code structure within components, architectural patterns have implications for the entire system. They primarily focus on these areas:

  • Large Scale Structure:

    • Overall structure and macro-architecture of entire packages (e.g., components in OSGi or modules and plugins in Eclipse).

  • Concurrency & Distribution:

    • Distributed systems and concurrency management.

  • Crosscutting Concerns:

    • Cross-cutting concerns across the entire system. These include, for example, strategies for error and exception handling, Startup/Shutdown procedures, or Monitoring.

#Examples of common Architectural Patterns

  • Layered Architecture: The system is divided into horizontal layers (e.g., Presentation, Business Logic, Data Access). Each layer typically may only communicate with the layer directly below it.

    • Benefits: Excellent separation of concerns, easier testing.
    • Liabilities: Lower performance (data must "bubble" through all layers), risk of the so-called sinkhole anti-pattern (a layer does no logic, just stupidly forwards data).

  • Event-Driven Architecture: Components do not communicate directly, but produce and consume asynchronous events (often via Publish/Subscribe).

    • Benefits: Extreme decoupling (producer does not know consumers at all), enormous scalability and flexibility when adding new features.
    • Liabilities: Very difficult debugging and loss of overview of the overall data flow through the system (traceability).

  • Pipes and Filters: A pattern absolutely ideal for sequential processing of data streams. Each "Filter" performs one isolated transformation on the data and passes it on through a "Pipe".

    • Benefits: Filters can be arbitrarily chained, swapped and reused.
    • Liabilities: Not suitable for interactive systems (e.g., UI), data often has to be constantly parsed and serialized between filters (which consumes performance).

  • Microservices Architecture: The application is broken into many small, independently deployable services forming separate domains.

    • Benefits: Agile development (teams do not step on each other's toes), ability to independently scale only loaded parts of the system.
    • Liabilities: Enormous increase in complexity in network communication, distributed transactions and monitoring.

#Example – Strangler Pattern

This is an exemplary architectural pattern for system modernization.

  • Problem:

    • We have a monolith that we want to rewrite into modern microservices, but we have to do it gradually to minimize risk and avoid outages.

  • Solution:

    • We gradually "strangle" functional parts of the monolith and build them into separate microservices. In front of all this, we place a "Strangler Facade" that transparently routes client traffic either to the old monolith or to the new services.

  • Benefits:

    • Significant risk reduction and ensuring continuous availability through traffic redirection at the gateway.

  • Liabilities:

    • There arises an enormous need to manage communication dependencies between the rest of the monolith and the new services, and often complex database replication must be addressed.

#How Scenarios, Tactics and Patterns fit together

As an architect, you proceed in a clear sequence:

  1. First, you define quality requirements through Quality Scenarios.
  2. Then, for the most important ones, you choose appropriate proven principles and strategies – Design Tactics.
  3. And only as the very last step do you look in the catalog for appropriate Design / Architectural Patterns that implement these selected tactics within the system.

#Example from practice – Hexagonal Architecture"

In the target architecture refactgoring for my Flexibility value stream, I am using the Hexagonal architecture pattern Port & Adaptor pattern.

  • Problem & Context: The goal was to create a approproate layered architecture following the DDD principle.
  • Solution (Patterns Applied):
    • Architectural:
      • Ports and Adapters (Hexagonal Architecture).
      • I have chosen the Hexagonal architecture pattern, this in one hand provies a way to make the diferent layers of the architecture viy infrastructure - domaion- application - presentation. .
    • Design: Adapter Pattern and Dependency Injection.
      • The core declared abstract adapter classes (Ports). Users implemented specific descendants (Adapters) and only pointers to these instances were passed to the core constructor (Constructor Injection).
  • Benefits:
    • Enormous flexibility – moving all platform dependencies into adapters.
    • Reusability – the abstract interface could be recycled for other generic cores in future projects.
  • Liabilities (Disadvantages/Trade-offs):
    • The resulting source code became somewhat more voluminous.
    • Worse code readability at first glance due to a high degree of abstraction and pointer passing (indirection).
