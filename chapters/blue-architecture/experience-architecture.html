#1. Systematic architecture design — Flex RT (Flexibility Manager for Operations)

Source: Systematic-architecture-design.md

Situation. Flex RT is a product before product-market fit: the business goal itself was still a hypothesis. Wide solution space, thin knowledge — exactly where Big Design Up-Front is waste. The architecture had to be grown, not specified.

What I did. Ran the full L-model in every iteration:

  • Vertical: requirements elicited from real use cases with the co-innovation partner → domain model built through Event Storming (the discovered events later became the Kafka topics) → dynamics of scenarios → explicit scope & boundaries.
  • Horizontal: conceptual draft → baseline architecture → deployment views → goals, principles & guidelines → planned increments.
  • Phases with nothing new became a no-op but were never dropped.
  • Maturity stages actually traversed: Initial draft (sketch from event storming, for stakeholder review) → Walking Skeleton (one high-risk flow end-to-end at production quality, real interfaces + deployment + test setup) → MVP released to the co-innovation partner to validate product-market fit.
  • Documentation kept to the pyramid: System → Subsystem/Service → Component, with cross-cutting concerns (security, observability, unit/multiplier, API conventions) documented once.

Lesson. Before product-market fit the Walking Skeleton is the cheapest risk reducer. Event Storming replaces a heavy UML domain model and produces alignment as a by-product. Running the whole L-model per iteration is the discipline that prevents erosion — skipping the "boring" phases (boundaries, deployment) is what makes architecture drift.

#2. Architecture documentation — the missing E2E runtime & latency budget diagram

Source: Architecture-documentation.md

Situation. In Flexibility Operation Planning nothing described the end-to-end runtime path of a flexibility request, and no latency budget was assigned per hop. Every team documented its own service, so every component looked fine in isolation. The missing view was the Process View (4+1) — the one that makes cross-service timing visible.

What I did. Created the missing E2E runtime view: all services on one path, each hop annotated with measured time and its allowed budget, compared against the business deadline. Kept at subsystem level (one readable page), then used it as a communication instrument towards the Product Manager — it proved the budget was exceeded structurally, not because one service was slow, so no local optimisation could fix it. On that basis the larger architecture refactoring was accepted and prioritised.

Lesson. A missing view hides a real defect. A latency budget turns a quality requirement into a checkable per-hop contract. Documentation is communication — the diagram fixed nothing technically, it created the shared understanding that unlocked the decision.

#3. ADR — turning ADRs into an architecture fitness function

Source: ADR-architecture-decision-records.md

Situation. The NGM group already had an ADR culture: the MADR template, a review process, the wiki as source of truth. The process worked; the scale did not. Past 110 ADRs: nobody could find the right decision, nothing verified that the code still obeyed it (e.g. the Kafka topic naming convention), and teams started seeing ADRs as bureaucracy.

What I did. Treated ADRs as executable constraints, not documentation:

  • Wiki → Markdown in the repo (Docs as Code), same MADR template, versioned next to the code.
  • Pull Request per decision — review on the PR, merge = approval, git log = decision history, supersession traceable.
  • Indexed all ADRs into the NGM context ("engine brain") → findable in natural language, not by title.
  • ADRs loaded into the agent's context before coding — the decision shapes the code at authoring time.
  • Validation as a fitness function — the agent checks source code against applicable ADRs and reports violations with a link back to the deciding record.

Lesson. A decision that cannot be found does not exist (past ~50 records retrieval, not authoring, is the bottleneck). An unverified decision degrades into an opinion — automate the check where the rule is machine-checkable (naming, layering, dependencies). Adoption follows value, not mandate.

#4. Goals-Principles-Decisions — unit multiplier standard (NGM / CIM)

Source: Goals-Principles-Decisions.md

Situation. Every process value in NGM is a physical quantity (50 kV = value 50 + multiplier k + unit V). Components hard-coded unit and multiplier, assumptions were out of sync along the processing chain and only negotiated developer-to-developer. Mismatches surface only when test-driving the code — and in grid operation a wrong multiplier can drive a wrong decision on the electrical grid.

The GPD chain.

  • Goal: correctness & consistency of physical values, maintainability, independence from external model changes.
  • Principles: use the CIM electricity data type (value + unit + multiplier, IEC 61970-301); NGM fixes one unit/multiplier per data type so internal APIs don't transport it at runtime; convert only at the system boundary.
  • Decisions: unit/multiplier part of every API/profile spec (self-contained APIs); for measurements/controls replace unitMultiplier + unitSymbol with a single measurementValueType attribute driven by an NGM enum (a conscious, documented deviation from CIM); maintain a central multiplier-per-type table as the single source of truth.
  • Example: TransformerEnd.ratedS goes from a plain double (kVA in one service, MVA in the next) to ApparentPower, always MVA, known from the spec rather than sent at runtime.

Lesson. The chain makes the decision defensible instead of a personal preference — when domain experts challenged the chosen multipliers (base units vs. kV/kW/kVA/kVAr for MV/LV grids), the discussion could be held at the level of the principle and the decision re-opened without touching the goal. That traceability is exactly what GPD is for.

#5. Quality scenarios & design tactics — Claim-Check for the congestion interface

Source: Quality-scenarios-and-design-tactics.md

Quality attribute: Scalability. The number of congested equipment (EQ) items per case is data-driven, not design-driven.

Element Content
Source Congestion Prediction service
Stimulus EQ count per case scales from ~10 to 10,000+ (≈80 % of the grid congested)
Artifact Interface between Congestion Prediction and Congestion Prevention
Environment Peak congestion / unhappy path
Response Event stays small; detail data fetched in throttled batches
Response measure Kafka message size bounded regardless of EQ count; no single operation carries the full volume

Tactic — Claim-Check with batched deferred resolution. Prediction publishes CongestionPredicted { caseId, eqIds[] } (identifiers only) on siemens-gsw.congestion-prediction.congestion-predicted.1; Prevention resolves the P/Q values through a bounded batched REST query. More EQ means more batches, not bigger messages.

Scope & trade-off. Not a performance tactic (nothing gets faster) and not a resilience tactic (no retry/circuit-breaker). The cost is a synchronous runtime dependency and added latency — accepted because the alternative (everything in the Kafka message) has a hard structural ceiling that cannot be engineered around.

#6. Architecture refactoring — Flex OP cyclic dependency

Source: Architecture-refactoring.md

Smell (internal signal). A forecasted measurement was consumed by two services — one presenting it in the UI, one detecting violations. The violation service also had to read the actual measurement back from the measurement repository, closing a cyclic dependency. Symptom: unpredictable, flaky end-to-end tests.

What I did. Identified the cycle as the root cause (not the tests), introduced continuous polling as a deliberate short-term workaround to stabilise delivery, and documented that it is not the target solution. The real fix (breaking the cycle via dependency inversion / event-driven hand-over) was sized, prioritised with the Product Owner and put on the backlog.

  • Planning level: Component → Backlog item (Team + PO).
  • Technical debt quadrant: Deliberate + Prudent — conscious debt with an explicit repayment plan.

Lesson. Proactive, small, sellable refactoring beats waiting until only a rewrite is left.

#7. Architecture refactoring — case expiry via TTL (Valkey)

Source: Architecture-refactoring.md

Smell. No central orchestration for the rule "a case expires after 24 hours". The first solution was UI-driven: when the UI opened a case, the API checked the age and only then flipped the state to expired. The business state therefore only existed if somebody looked at it — the trigger lived in the wrong place.

What I did. Moved the lifecycle out of the UI into the platform: cases are held in an in-memory store (Valkey) with a TTL, and TTL expiry itself emits the event that expires the case. State becomes correct by construction, independent of user interaction. External behaviour preserved, organisation changed.

  • Technical debt quadrant: the original design was Inadvertent + Prudent — corrected once we understood that a lifecycle rule must not depend on a UI trigger.

Lesson. An architecture smell is often not "ugly code" but a trigger sitting in the wrong component. Fixing ownership of the trigger removed a whole class of inconsistent-state defects.

#8. Architectural & design patterns — Hexagonal architecture in the Flexibility value stream

Source: Architectural-and-Design-Patterns.md

Problem & context. Target architecture refactoring for the Flexibility value stream needed a proper layered structure following DDD principles.

Solution. Ports & Adapters (Hexagonal Architecture) as the architectural pattern, separating infrastructure – domain – application – presentation. Supported by the Adapter pattern and Dependency Injection: the core declares the abstract ports, concrete adapters are implemented outside and injected via the constructor.

Benefits / liabilities. Flexibility — all platform dependencies live in adapters; reusability of the abstract interfaces. Cost: more code volume and worse first-glance readability due to the indirection.

Order that matters (for the exam). Quality Scenarios → Design Tactics → only then Patterns. The pattern is the last step, never the starting point.

#9. Architecture in an agile environment — CRR, no big up-front design

Source: Architecture-in-agile-environment.md

Context. In the Flex target architecture (CRR) we agreed on feature parity with no up-front design — starting from a happy-path flow instead.

What I did / what we agreed. With many unknowns still open, we chose incremental design, iteration and validation rather than an up-front "bulletproof" solution — while insisting that the happy paths are built at real quality, not as throwaway code. ACL (anti-corruption layer) was introduced only where actually required.

Lesson. Simplicity before generality and decide at the last reasonable moment are the two agile principles most easily violated by architects — the pull towards BDUF is strongest exactly when the unknowns are largest.

#10. Domain-driven design — DDD in Flex OP and Flex RT

Source: Domain-driven-design.md

Where it applies. Both Flex OP and Flex RT are modelled with DDD: the domain layer is clean and depends on nothing; the application layer coordinates; the infrastructure layer depends on the domain and implements the repository interfaces the domain defines (dependency inversion). This is the same decision as the Hexagonal pattern in entry 8 — the pattern is how the DDD layering is realised.

#Cross-cutting lessons (what ties the examples together)

  • Make the invisible visible. The latency diagram, the ADR index, the cycle in the dependency graph — in each case the fix started by producing an artefact that let other people see the problem.
  • Short-term workaround + documented repayment ≠ sloppiness. Polling (entry 6) and the UI check (entry 7) are only acceptable because the quadrant and the backlog item were explicit.
  • Decide against the drivers, not against opinions. GPD (entry 4) and MADR (entry 3) both exist so that a decision can be re-opened on its principle, not re-litigated from scratch.
  • Bound what grows. The Claim-Check (entry 5) and the latency budget (entry 2) are the same instinct: find the dimension that scales with data, and put a ceiling on it.
  • Architecture is a social activity. Product Owner, Product Manager, domain experts and the co-innovation partner appear in almost every example — the technical insight was never the hard part.
