🔵 Architecture Documentation

#What we document — definition of Architecture

There is no single universal definition, but they all revolve around similar concepts:

  • ANSI/IEEE (1471-2000): Architecture is the fundamental organization of a system embodied in its components, their relationships to each other and to the environment, and the principles governing its design and evolution.
  • Grady Booch (2006): Architecture represents significant decisions about the design that shape a system, where "significant" is measured by the cost of change.
  • Ralph Johnson: Architecture is simply "about the important stuff" ("Architecture is about the important stuff... whatever that is").
  • Shosh's view: Every system has architecture (good or bad, documented or not) and it can exist (e.g., as plans) even before the actual implementation. Wolfgang adds that it is everything that helps discuss significant requirements and qualities.

#Why we document

Documentation is first and foremost communication. It must clearly answer: Why we are documenting (Purpose), Who cares about it (Stakeholder), and What information they need (Content).

#How we document — Architectural Views

Architecture cannot be described with a single diagram. Different stakeholders need different views.

#The 4+1+n Views concept

  • Use Case View: The focal point for end users.
  • Logical View: A description of functionality for the end user.
  • Process View: Addresses runtime and dynamic infrastructure (performance, scalability, startup scenarios) for system integrators.
  • Implementation/Development View: Addresses code and software management for developers.
  • Physical/Deployment View: Topology, delivery, installation, and communication for systems engineering.
  • Additional views: Context, Data, Variability, Migration.

#C4 Model (Modern alternative to 4+1 Views)

In practice, the C4 model is widely used today:

  • Context — a view of the overall system (management, business, non-technical stakeholders)
  • Containers — large functional blocks, e.g., database, web client, technologies used (architects, DevOps, developers)
  • Components — inside a single container, what it is made of and how it interacts (developer)
  • Code — detail of a single component, e.g., a UML class diagram (developer). This is already a very detailed level, it becomes outdated quickly, is hard to keep up-to-date, and is only appropriate for key algorithms.

#Rules and Best Practices

  • Process documentation with the same attention to quality as code (versioning, change management, refactoring) and always write from the reader's perspective.
  • Avoid repetition and ambiguity (start writing a glossary).
  • Every document must have one definitive owner (responsible) and the documentation overview should not exceed 50 pages to remain readable.
  • Keep documentation current, "but not too current" ("Keep the documentation current but not too current") and review it regularly to ensure consistency.
  • Use established templates, e.g., from the organization or the popular arc42. The advantage of templates is structure; the disadvantage can be the risk that they are either incomplete (Incomplete) or overloaded with information (Too Much). Rule: Do not delete any part of a template ("Do not delete any part in templates").

#Tools and Modelling

We distinguish between two approaches to creating documentation:

  • Drawing Tools: Gliffy, Visio, Draw.io, or text-based PlantUML.
    • Advantages: They are lightweight and provide a great degree of freedom.
    • Disadvantages: Lack consistency checking and do not support working with large interconnected models.
  • Modelling Tools: MagicDraw, Enterprise Architect.
    • Advantages: They offer Cross-Model Consistency and form a knowledge base, e.g., even for code generation.
    • Disadvantages: Less freedom and a much steeper learning curve.

#Architect's role and responsibilities (SWA)

A software architect in the context of documentation must:

  • Define which views (views) are needed.
  • Keep these views mutually consistent.
  • Document decisions taken (e.g., via ADRs).
  • Regularly review the documentation and verify that it is current.

#Real-world example: The missing E2E flexibility runtime & latency budget diagram

#Situation

In Flexibility Operation Planning, no view described the end-to-end runtime path of a flexibility request — from forecast/measurement ingestion, through prediction and prevention, to the dispatched flexibility — and no latency budget was assigned to the hops along that path. Each team documented its own service, so every component looked fine in isolation. What was missing was the Process View (runtime and dynamics) in 4+1 terms: the one view that makes cross-service timing behaviour visible. The consequence was a classic documentation gap — the problem was real and measurable in production, but nobody could point at it.

#My actions (Applying the theory)

  • Created the missing E2E runtime view: all participating services on one path, every hop annotated with its measured time and the budget it is allowed to consume, so the total could be compared against the business deadline.
  • Deliberately chose the right level of the pyramid — subsystem/service, not code. One page, readable by a non-technical reader.
  • Used it as a communication instrument towards the Product Manager and stakeholders: the diagram showed that the budget was exceeded structurally, not because one service was slow — so no local optimisation could fix it.
  • On that basis, the need for a larger architecture refactoring was accepted and prioritised into the backlog, instead of being argued as a developer opinion.

#Evaluation and lessons learned

  • A missing view hides a real defect. Every service being individually "within spec" while the end-to-end flow misses its deadline is exactly what the Process View exists to reveal.
  • A latency budget turns a quality requirement into a documented, checkable contract per hop — and makes the offending hop undeniable.
  • Documentation is communication: the diagram did not fix anything technically; it created the shared understanding that unlocked the budget and the decision. That is the point of documenting — picking the view the stakeholder needs, not the one the architect finds interesting.
